Secrets that never

A production-grade, security-hardened Docker Compose environment demonstrating how an autonomous AI agent manages encryption keys, session data, and long-term memory with zero tolerance for plaintext at rest.

Core Promise

The Fernet encryption key lives only in RAM — fetched from OpenBao at runtime via AppRole authentication, never written to any file, automatically wiped if the secrets manager becomes unreachable.

Why This Exists

Autonomous AI agents are increasingly entrusted with sensitive context: conversation history, API credentials, long-term memory. The naive approach — writing session data to disk, storing keys in environment variables — creates a forensics nightmare. A stopped container leaving plaintext on disk is a liability.

This design demonstrates a layered approach where secrets are sourced from a dedicated vault, encryption happens at the application layer before any bytes hit persistent storage, active sessions live exclusively in RAM, and a dead man's switch ensures key material is wiped if the secrets manager goes dark.

3 Security Layers

Eight independent security layers, each defending against a different attack surface. Compromise of any single layer does not yield plaintext data or persistent access.

🔑
Fernet Encryption — Crown Jewel
HMAC-SHA256 + AES-128-CBC · Authenticated encryption
Layer 1

All persistent session data is encrypted with a Fernet key before any bytes touch the workspace volume. Fernet provides authenticated encryption — tampered ciphertext is rejected with InvalidToken before any data is returned.

The token format is gAAAAA... (base64url), self-describing with a timestamp. The 32-byte key is generated fresh on every openbao-init run using /dev/urandom.

Algorithm AES-128-CBC + HMAC-SHA256 (cryptography.fernet) Key size 32 bytes (256-bit) — base64url-encoded to 44 chars Key source OpenBao KV: kv/openclaw/encryption.fernet_key Key storage Python heap only — never written to any file Key lifetime Wiped on dead man's switch or SIGTERM Key rotation Re-run openbao-init → new key → existing data unreadable Token prefix gAAAAA (indicates valid Fernet token format)
🧠
tmpfs RAM Isolation
Sessions, secrets, and cache live in RAM — never on disk
Layer 2

Three mount points are configured as tmpfs (Linux RAM-backed filesystem). Data written to these paths never touches the host's physical storage. When the container stops or is killed, all contents are immediately gone — no forensic recovery possible.

/openclaw/sessions 64MB tmpfs — active conversations (plaintext, RAM only) /openclaw/secrets 10MB tmpfs — manifest only (actual secrets in Python heap) /openclaw/cache 128MB tmpfs — model cache, temp computation /tmp 32MB tmpfs — gunicorn/Flask runtime scratch Verification GET /status → mounts.tmpfs_mounts[path].is_tmpfs=true
✅ Active session data (POST /session/active) is stored in both the Python in-process dict and the tmpfs filesystem — dual RAM isolation. Neither location persists across a container restart.
💀
Dead Man's Switch
3 consecutive OpenBao failures → wipe all secrets from RAM
Layer 3

A background daemon thread polls OpenBao's /v1/sys/health every HEARTBEAT_INTERVAL seconds (default 30s). If the health check fails three consecutive times, all in-memory secrets are atomically wiped: Fernet key, API keys, config, and token are zeroed out.

If OpenBao comes back online, the daemon automatically re-authenticates via AppRole and re-fetches all secrets — no manual restart required.

Check interval 30s (configurable via HEARTBEAT_INTERVAL env var) Threshold 3 consecutive failures before wipe Wipe scope Fernet key, API keys, config, auth token — all secrets Recovery Automatic re-auth + re-fetch when OpenBao returns Wipe count Tracked in GET /status → dead_mans_switch.wipe_count Log message 💀 DEAD MAN'S SWITCH — wiped all secrets from memory
🔥
SIGTERM / SIGINT Shred Trap
Container stop → 3-pass overwrite → unlink → exit
Layer 4

Python signal.signal(SIGTERM, _shutdown_handler) registers a cleanup routine. When Docker sends SIGTERM (on docker stop or docker compose down), the handler fires before the process exits.

The 3-pass overwrite pattern (zeros → ones → 0xa5) follows the DoD 5220.22-M pattern. On SSDs, the OS may remap writes to different physical cells, but this is the best achievable at the software layer without hardware-level secure erase. On tmpfs mounts, overwrite + unlink is an effective wipe (no underlying persistent storage).

python 
# 3-pass overwrite before unlink
with open(path, "r+b") as f:
    # Pass 1: zeros
    f.seek(0); f.write(b'\x00' * size); os.fsync(f.fileno())
    # Pass 2: ones
    f.seek(0); f.write(b'\xff' * size); os.fsync(f.fileno())
    # Pass 3: 0xa5 pattern
    f.seek(0); f.write(b'\xa5' * size); os.fsync(f.fileno())
path.unlink()  # remove directory entry
Triggers SIGTERM (docker stop), SIGINT (Ctrl+C) Shred order 1. wipe_secrets() 2. shred_workspace() 3. wipe tmpfs files Passes 3 (zeros, ones, 0xa5) + fsync after each Scope All .enc files in /openclaw/workspace/**
🔒
Read-Only Root Filesystem
Immutable container image at runtime
Layer 5

read_only: true in docker-compose.yml mounts the container's root filesystem as read-only. Any attempt to write to paths not explicitly listed as volumes or tmpfs mounts fails with EROFS.

Writable paths are explicitly declared: the four /openclaw/* paths, /tmp, /app/__pycache__, and /var/run — all either tmpfs (ephemeral) or declared volumes (workspace).

Docker Compose read_only: true Effect Root filesystem immutable — writes to unspecified paths fail Prevents Malicious code writing secrets to image layers
👤
Non-Root Execution (UID 10001)
Privilege drop via os.setuid() at startup
Layer 6

The Dockerfile creates a dedicated openclaw user (UID/GID 10001). The container starts as root (to chown tmpfs mount points), then the entrypoint drops to UID 10001 before executing the Flask application.

Combined with no-new-privileges: true, the app cannot escalate back to root via setuid binaries or other privilege escalation vectors.

UID/GID 10001 / 10001 (openclaw:openclaw group) Drop mechanism Entrypoint chown → exec as UID 10001 Capabilities cap_drop ALL; cap_add SETUID, SETGID, CHOWN, DAC_OVERRIDE Escalation security_opt: no-new-privileges:true blocks setuid escalation Verification GET /status → security.uid = 10001 (never 0)
🎭
AppRole Least-Privilege Auth
No root token in app — machine auth with read-only policy
Layer 7

The app never sees the OpenBao root token. It authenticates via AppRole: reading a role_id + secret_id (UUID-format, not secrets) from a shared volume written by the init container. These credentials produce a short-lived token (1h TTL, 4h max) with read-only access to exactly three KV paths.

Auth method auth/approle/login (role_id + secret_id → token) Token TTL 1h renewable (max 4h) Policy openclaw-policy: read kv/openclaw/{encryption,api-keys,config} Capabilities read only — no write, no delete, no admin paths Token renewal Dead man's switch renews token before expiry; re-auths if needed Root token NOT present in app container environment
🚫
Zero Secrets in Env Vars / Image Layers
All secrets fetched at runtime — never baked in
Layer 8

Docker images are immutable and their layer history is inspectable. Any secret baked into a ENV directive or RUN command is permanently readable from the image. This design bakes in zero secret material.

The Dockerfile ENV directives contain only non-secret configuration: BAO_ADDR (just an address), FLASK_ENV, and PYTHONUNBUFFERED. The actual Fernet key, API keys, and JWT secrets exist nowhere in the image or environment — they are fetched live from OpenBao on every startup.

Image layers No FERNET_KEY, no API keys, no secrets of any kind docker inspect env Contains only non-secret config (addresses, log levels) /proc/1/environ No secret material — verified by test suite (Test 4) Secret acquisition AppRole login at startup → Fernet key stored in Python heap

Init Sidecar
openclaw-openbao-init
one-shot · exits after setup

A one-shot initialization container that bootstraps OpenBao's secrets and AppRole configuration. Uses the same OpenBao image — no extra tooling required. Runs to completion then exits with code 0, which satisfies the condition: service_completed_successfully dependency in docker-compose.

Init Steps (7 phases)

1
Wait for OpenBao
Poll /v1/sys/health until ready (30 attempts, 2s apart)
2
Enable KV v2 Engine
Enable KV v2 at path kv/ (skips if already mounted)
3
Generate Fernet Key
32 bytes from /dev/urandom → base64url-encode → store at kv/openclaw/encryption. Key is 44 chars, URL-safe, fresh on every init run.
4
Write App Secrets
Generate simulated API keys (openssl rand -hex), JWT secrets, and config. Write to kv/openclaw/api-keys and kv/openclaw/config.
5
Create OpenClaw Policy
HCL policy granting read access to encryption, api-keys, and config paths. Also allows token self-renewal and self-lookup. No write or admin access.
6
Configure AppRole
Enable AppRole auth method, create openclaw-role with openclaw-policy, generate role_id and secret_id.
7
Write Credentials to Shared Volume
Save role_id and secret_id to /approle-creds/ (named volume shared with app). These are UUID-format identifiers — not secrets.
App
openclaw-app
:8300 · Flask API

The OpenClaw agent simulator. Python 3.12 on python:3.12-slim. Runs as UID 10001 with a read-only root filesystem, all capabilities dropped, and no secrets in the environment. Handles session encryption/decryption, active session RAM storage, and the dead man's switch background thread.

POST /session/save Encrypt + persist session to workspace volume

Encrypts the provided data with the Fernet key (from OpenBao) and writes it to /openclaw/workspace/session_{id}.enc. The volume contains only Fernet ciphertext — no plaintext. Returns 503 if the key isn't loaded. Session IDs must be alphanumeric + hyphens/underscores, max 128 chars.

Request
json 
{ "session_id": "sess-123", "data": "any string data" }
200 Response
json 
{
  "status": "saved",
  "session_id": "sess-123",
  "storage": "workspace (encrypted)",
  "encrypted": true,
  "key_source": "openbao",
  "note": "Data encrypted with Fernet before disk write"
}
GET /session/load/<id> Decrypt + return session from workspace volume

Reads the .enc file from workspace, decrypts with the Fernet key, and returns plaintext. Returns 404 if not found, 422 if ciphertext is tampered (Fernet InvalidToken), 503 if key isn't loaded.

200 Response
json 
{
  "status": "loaded",
  "session_id": "sess-123",
  "data": "any string data",
  "source": "workspace (decrypted)"
}
POST /session/active Store active session in RAM (tmpfs) only — never persisted

Stores session data in two RAM-only locations: the Python process dict and a file in /openclaw/sessions/ (tmpfs). This data is never written to the workspace volume. Lost on container restart. Use /session/save for persistence across restarts.

Request
json 
{ "session_id": "live-456", "data": "live conversation state" }
200 Response
json 
{

  "session_id": "live-456",
  "storage": "tmpfs-ram (not persisted)",
  "encrypted": false,
  "note": "Use /session/save for encrypted persistence across restarts"
}
GET /session/active/<id> Retrieve active session from RAM

Retrieves a session from the in-process dict. Returns 404 if not found (may have been wiped by dead man's switch). The stored_at timestamp shows when it was created.

200 Response
json 
{
  "status": "found",
  "session_id": "live-456",
  "data": "live conversation state",
  "stored_at": "2026-03-26T20:00:00Z",
  "storage": "tmpfs-ram"
}
DELETE /session/<id> Secure delete — 3-pass overwrite + unlink + RAM clear

Securely deletes a session from both workspace (encrypted volume) and active sessions (RAM). Workspace file: 3-pass overwrite (zeros, ones, 0xa5) + fsync after each pass + unlink. Active session: removed from Python dict and tmpfs file securely deleted. Returns 404 if neither location had the session.

  • Root filesystem is read-only (cannot write to /)
  • /tmp is writable (correctly allowed)
  • /openclaw/sessions is writable (tmpfs, correctly allowed)
  • /openclaw/workspace is writable (volume, correctly allowed)
  • /openclaw/secrets is writable (tmpfs, correctly allowed)
  • /openclaw/cache is writable (tmpfs, correctly allowed)

8 Threat Model

Honest assessment of what this architecture protects against and what requires additional mitigations. No silver bullets — know your threat surface.

✅ Protected Against
✅
Disk forensics after shutdown
SIGTERM shred trap + tmpfs wipe means no plaintext survives container stop. Fernet-encrypted workspace contains only opaque ciphertext.
✅
Container escape reading workspace
Even if an attacker escapes to the host and reads the workspace-data volume, they see only Fernet ciphertext — useless without the key.
✅
Secrets leaking via env vars
Zero secrets in environment variables or image layers. Verified by test suite (Test 4) via /proc/1/environ and docker inspect.
✅
API endpoint information disclosure
No endpoint exposes key material. /status shows key names but not values. AppRole credentials are UUIDs — not application secrets.
✅
Rogue app writing secrets to disk
Read-only rootfs prevents writing to unspecified paths. cap_drop ALL limits privilege abuse.
✅
OpenBao network partition / compromise
Dead man's switch wipes Fernet key after 3 failed health checks. Encrypted sessions become unreadable — chosen over leaving key in RAM indefinitely.
✅
Path traversal in session IDs
Session IDs validated with ^[a-zA-Z0-9_\-]{1,128}$ regex. Cannot traverse outside /openclaw/workspace/ via crafted IDs.
✅
Ciphertext tampering
Fernet provides authenticated encryption (HMAC-SHA256). Modified ciphertext raises InvalidToken before any data is returned.
❌ Not Protected Against
❌
Host-level memory dumps
The Fernet key is in the Python heap. A root-level host process reading /proc/{pid}/mem would find it. Mitigate with SELinux/AppArmor on the host.
❌
Hardware-level attacks (cold boot, DMA)
Cold boot attacks can recover RAM contents after power loss. DMA attacks via PCIe devices can read physical memory. Mitigate with HSM for key management.
❌
Compromised Docker daemon
If the Docker daemon itself is compromised, all bets are off. The design relies on Docker's security model for isolation.
❌
SSD data remanence (without LUKS)
SSD wear-leveling may not honor overwrite requests to the same physical cells. The 3-pass shred is best-effort on SSDs. LUKS encryption on the host volume is the correct solution for production.
❌
Kernel vulnerabilities / container escape
A kernel exploit that gives an attacker container escape and memory read access can extract the Fernet key. No software-only solution prevents this.
❌
Swap — if host has swap enabled
If the host has swap enabled, Python heap pages (including the Fernet key) may be swapped to disk. Use --memory-swap or disable host swap.

Production Hardening Recommendations

RiskMitigationEffort
Memory dumps SELinux/AppArmor profiles, gVisor sandbox Medium
SSD data remanence LUKS-encrypt the host volume backing workspace-data Low
Key management at scale DEK/KEK key hierarchy — DEK encrypted by master KEK in HSM High
Swap leakage Disable host swap or use encrypted swap (zswap/zram) Low
API exposure Add mTLS or API key authentication to Flask endpoints Low
OpenBao persistence Use Raft or Consul backend instead of dev-mode in-memory Medium
Secret rotation Implement DEK versioning for key rotation without data loss High

Key Rotation Procedure

⚠️ Rotating the Fernet key makes all existing encrypted workspace sessions unreadable. This is by design — forward secrecy. Before rotating, either export all sessions via GET /session/load/* or accept that historical data is abandoned.
bash 
# 1. Rotate key — generates new Fernet key in OpenBao
$ docker compose run --rm openbao-init

# 2. Restart app to pick up new key
$ docker compose restart openclaw-app

# 3. Verify new key loaded
$ curl http://localhost:8300/health | jq .encryption
true

# Note: existing .enc files are now undecryptable (wrong key)
# This is intentional — forward secrecy
